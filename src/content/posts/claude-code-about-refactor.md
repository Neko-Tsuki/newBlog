事情是这样的——

「关于我」这个页面，咱自己前前后后改了大概……嗯，数不清多少遍了。每次都是「给这张卡片加点圆角」「把这个间距调大一点」「加个渐变色」，改完看一眼，总觉得哪里不对，然后关掉编辑器。

到头来就是越改越乱。

尤其从「关于本站」往下那一段，简直没法看。咱一度以为是自己审美不行，后来才发现……**不全是审美的问题，是真的有 bug**。这个后面讲。

## 一、这次咱学乖了：先让它自己看

以前咱用 AI 改东西，习惯是张嘴就来：「帮我把这个页面改好看点」。

结果嘛……你也能猜到。它一顿操作，改出来的东西说不上丑，但也说不上好看，就是那种**很努力但方向不对**的感觉。~~像极了咱当年写作文硬凑字数。~~

这次咱换了个思路——**先不说改什么，先让它看现状**。

咱就丢了一句：

> 帮我重构一下我的「关于我」页面，主要从`<关于本站>`往下很乱，上面部分排版比较混乱

然后它干的第一件事，不是动代码，而是**截图**。

### 顺带说个咱觉得挺妙的技巧

它发现咱这机器上装了 Floorp（Firefox 的衍生版），就用 headless 模式去截图：

```bash
floorp --headless --no-remote --profile /tmp/某临时目录 \
  --window-size=1200,5200 --screenshot /tmp/out.png "file:///..."
```

这里有个坑得提一嘴：**必须另开一个 profile 加 `--no-remote`**，不然它会去连你正在用的那个浏览器实例，然后报一句「Floorp is already running」把你晾在那儿。

咱当时就想：好家伙，这玩意儿还会自己找工具使唤。

## 二、它列出的问题，有几个咱压根没发现

截完图之后，它给了咱一张清单。咱看了一眼，有点沉默。

| # | 问题 | 咱之前发现了吗 |
|---|------|--------------|
| 1 | 正文里 `9:07` 被渲染成了 `9<07></07>` | 完全没发现 |
| 2 | 一页里有**两个** `<h1>` | 没发现 |
| 3 | 全文有 **6 条** `---` 分隔线，把页面切得很碎 | 感觉到了，但说不清哪儿不对 |
| 4 | 「附加功能」表格的「来源」列，6 行全是 `Firefly-hyde` | 没发现 |
| 5 | 表格后面那段话**重复了表格内容** | 没发现 |
| 6 | `> ::github{...}` 把两张卡片塞进了引用块里 | 觉得怪 |
| 7 | `ContactCard` 组件内联在 MDX 里，整个函数近百行 | 这个咱知道，一直懒得管 |
| 8 | 内容高 3401px，对「关于我」来说太长了 | 感觉到了 |

说白了，**咱只感觉到了「不对劲」，它给的是「哪儿不对劲」**。

### 重点讲讲第 1 条，这个坑有点意思

咱的原文写的是：

```text
一个在早上 9:07 分会和猫讨论量子披萨配方的：
```

构建出来的 HTML 是：

```html
早上 9<07></07> 分
```

**`<07></07>` 是个 HTML 标签**。为什么会这样？

因为主题的 markdown 插件链里有个 `remark-directive`，它负责解析 `::github{repo="..."}` 这种指令语法。但它的语法里还有一种 **text directive**，写法是 `:名字[内容]{属性}`——于是 `:07` 被它当成了一个叫 `07` 的指令，转成了标签。

```text
9:07  →  9 + [:07 指令]  →  9<07></07>
```

咱盯着这个 `9:07` 看了不知道多少回，愣是没发现。~~大概是脑子自动帮咱补全了。~~

**这个坑是全站性的**：任何 `10:30`、`9:07` 这类写法都会中招。修复也简单，转义一下就行：

```markdown
早上 9\:07 分
```

（咱没让它在插件层面改，因为那会影响全部内容，风险更大。先记着。）

看到 8 个问题之后，咱以为它要开始动手了。

结果它反过来问咱：

> 重构力度到哪一步？

然后给了三个带 **ASCII 预览图** 的选项：

```text
【中等：卡片化重排】
┌─ Astro ──┐ ┌─ Fuwari ─┐
│ 核心框架  │ │ 视觉风格  │
└──────────┘ └──────────┘
┌─ Waline ─┐ ┌─ Firefly ┐
│ 评论系统  │ │ 主题模板  │
└──────────┘ └──────────┘
```

还有一题问顶部区怎么处理，因为它发现 **banner 上已经有「关于我」标题了**，内容里再放一个 H1 是重复的。

咱选了「中等：卡片化重排」+「名片式卡片」。

说真的，这一步是咱最没想到的。**它没有瞎猜咱想要什么风格，而是把选项摆出来让咱挑**。以前咱用 AI 改 UI，最大的痛点就是「它改的确实是它理解的，但不是咱想要的」，来回扯皮。这次一次到位。

## 四、卡片化是怎么落地的

它建了三个组件，放在 `src/components/pages/about/` 下面：

| 组件 | 干嘛的 |
|------|--------|
| `AboutHero.astro` | 名片卡片：头像 + 名字 + 身份胶囊 + 签名 + 社交按钮 |
| `InfoCard.astro` | 通用信息卡，有 `href` 就渲染成可点的 `<a>` |
| `ContactCard.astro` | 联络卡片，从 MDX 里那个近百行的内联组件抽出来的 |

### 但真正关键的是这个：改用主题令牌

咱原来的 `ContactCard` 长这样：

```jsx
className="
  bg-white/50
  dark:bg-zinc-900/50
  border-zinc-200/40
  dark:border-zinc-800/40
  text-zinc-900 dark:text-zinc-50
  ...
"
```

看出来问题了吗？**全是硬编码的 `zinc` / `white`**。

这意味着它**完全不跟主题走**：你换了主题色相，它不变；你切亮暗，它靠 `dark:` 硬切，跟主题那套变量体系是两套东西。所以它看着「跟全站不搭」——不是错觉，是真的不搭。

改成主题令牌之后：

```jsx
class="bg-(--btn-regular-bg)
       hover:bg-(--btn-regular-bg-hover)
       text-(--deep-text)
       border-(--line-divider)"
```

这样主题色相一变，卡片跟着变；亮暗切换也是自动的。

咱觉得这是这次重构**最有价值的一步**——比「排版好不好看」重要多了。好看是主观的，**跟主题一致是客观的**。

## 五、然后咱就翻车了：暗色模式下标题看不见

改完之后咱切到暗色模式看了一眼……

标题糊成一团。**基本看不见。**

![暗色模式下「尘尘 (LuluChan)」几乎看不见了](/assets/images/about-refactor/before-dark-broken.webp)

咱把这个反馈丢回去，它查了一下，找到了根因：

```styl
/* variables.styl —— 整个文件里只有这一处定义 */
--deep-text: oklch(0.25 0.02 var(--hue))
```

`--deep-text` 是「正文/标题色」，值是个**深色**。但它在 `:root.dark` 里**没有对应的覆盖**——也就是说，暗色模式下它**仍然是深色**，压在卡片的暗底（`--btn-regular-bg`）上，那可不就看不见了嘛。

### 更离谱的是，主题作者早就踩过这个坑

它在主题里搜出来三处，注释写得明明白白：

```css
/* 暗色下 --deep-text 仍为深色，需覆盖为亮色文字 */
:global(.dark) .timeline-item-title {
  color: var(--btn-content);
}
```

`StepItem`、`TimelineItem`、`EventCard`，三个组件各自打了一遍同样的补丁。还有咱的 `waline-custom.css`，用 `!important` 硬编码颜色绕开。

**大家都在各自绕同一个坑。** 咱看完就想：这不该从根上修吗？

于是咱问了一句「能根治吗」，它就把这一整套都清了：

| 改动 | 说明 |
|------|------|
| `:root.dark` 补上 `--deep-text: oklch(0.75 0.02 var(--hue))` | 让它随主题翻转 |
| 新增 `--on-primary` | 恒为深色、**不**翻转 |
| 删掉三个组件里的重复补丁 | 已经冗余了 |
| 删掉咱关于页三个组件里的临时覆盖 | 统一用 `--deep-text` |

### 为什么要多一个 `--on-primary`？

因为它发现有两处是**另一个语义**：

```jsx
dark:bg-(--primary) dark:text-(--deep-text)
```

底色是 `--primary`（**浅色**强调色），文字用 `--deep-text`。这两处依赖 `--deep-text` **保持深色**——如果它跟着翻转，就变成**亮字压亮底**，同样看不见。

说白了：`--deep-text` 是「正文/标题色」，`--on-primary` 是「强调色上的文字色」，**这俩本来就不该是同一个令牌**。之前混用，才是问题的根源。

### 它是怎么验证的

它没有靠肉眼看截图下结论，而是直接量：

```text
亮色  --deep-text=oklch(.25 .02 245)   --on-primary=oklch(.25 .02 245)
暗色  --deep-text=oklch(.75 .02 245)   --on-primary=oklch(.25 .02 245)
```

`--deep-text` 翻转了，`--on-primary` 没动。

然后它还建了个**临时页面**，把受影响的四个组件（`ButtonLink` 徽章 / `EventCard` / `StepItem` / `TimelineItem`）单独渲染出来，亮暗两种模式各截一张，逐一确认可读——**验证完就把那个页面删掉了**。

![修复后暗色模式下标题正常](/assets/images/about-refactor/after-dark.webp)

咱觉得这个习惯挺好的：**改核心变量 → 找出所有受影响的地方 → 逐个验证 → 清理现场**。

## 七、说点真心话

咱一开始写这篇文章，标题起得挺夸张的——「我一辈子也想不出来的设计风格」。

但写完之后咱想说点实在的。

**它做出来的设计，咱自己大概率也能想出来**，无非是卡片、圆角、间距、图标那一套。真正让咱服气的不是「设计得多好看」，而是三件事：

1. **它先看现状，再动手**。咱自己改页面的时候，从来没耐心先坐下来把问题列清楚，都是「感觉不对就直接改」，所以越改越乱。

2. **它先问咱要什么，而不是猜**。带预览的选项，比「帮我把这个改好看点」高效一万倍。

3. **它顺手把根上的问题挖出来了**。`--deep-text` 那个坑，主题里三个组件各自绕、咱自己的 CSS 也绕，谁都没想着去修——因为「改核心变量影响面太大」。但它把影响面找全了，逐个验证，然后改了。

到头来，咱觉得**「设计风格」反倒是这次最不值一提的收获**。

真正值钱的是那个 `9:07` 的 bug、那个重复的 `<h1>`、那个藏在主题里、被四个人各自绕过去的 `--deep-text`。

~~所以说标题党是要付出代价的，咱现在得自己打自己脸。~~

写完这篇之后咱又想到一件事：**那个 `:07` 的坑还没从根上修**。

咱目前只是在文章里转义了一下，但全站任何 `10:30` 这种写法还是会中招。要不要在插件层面加个判断，咱还没想好——毕竟改插件影响的是**所有内容**，不像改一个页面那么可控。
